# 记忆三层设计

> 本文是原始设计稿，代码已抽成这个独立仓库。落地时的取舍见第十二、十三节；文件路径以本仓库为准。

## 一、三层结构

| 层 | 存什么 | 在哪 | 变化速度 |
|---|---|---|---|
| 人格层 | 助手是谁、怎么说话、不变的偏好 | `persona.md`（调用方提供） | 几个月改一次 |
| 事实层 | 状态、事件、约定 | SQLite 新表 | 每轮可能加 |
| 情景层 | 当前对话 | `messages` 表 | 每轮 |

人格层不进数据库，永远全文进上下文，不参与检索、不参与衰减。

## 二、状态与事件

一句话判据：**同一时刻只能有一个值的，是状态；可以很多个并存、按时间排的，是事件。**

- 状态：住处、当前设定到第几版、上次约定的事
- 事件：某天你说想加个新设定、某次你说不喜欢 AI 腔

状态会变，事件会累积。

## 三、表结构

### `facts`（状态类，版本化）

```sql
CREATE TABLE IF NOT EXISTS facts (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id      TEXT NOT NULL,
    subject      TEXT NOT NULL,     -- 键，如「住处」「当前项目」
    content      TEXT NOT NULL,
    as_of        INTEGER NOT NULL,  -- 这条状态生效的时间
    created_at   INTEGER NOT NULL,
    superseded_by INTEGER,          -- 被哪条取代；NULL = 当前有效
    importance   INTEGER DEFAULT 3, -- 1-5
    last_used_at INTEGER,
    use_count    INTEGER DEFAULT 0,
    suppressed   INTEGER DEFAULT 0
);
CREATE INDEX IF NOT EXISTS idx_facts_subject ON facts(user_id, subject);
```

同一个 `subject` 允许多行。旧的**不删**，只把 `superseded_by` 指向新的一行。进上下文时旧行标注「（已过时，X 月）」。这就是人处理旧记忆的方式：不是忘掉，是记得「那是以前」。

### `memories`（事件类，累积）

```sql
CREATE TABLE IF NOT EXISTS memories (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id      TEXT NOT NULL,
    title        TEXT NOT NULL,     -- 索引，不是内容
    content      TEXT NOT NULL,
    keywords     TEXT,              -- 逗号分隔，手动或抽取
    as_of        INTEGER NOT NULL,
    created_at   INTEGER NOT NULL,
    source_from  INTEGER,           -- 摘要压缩时的原始消息 id 起点
    source_to    INTEGER,           -- 终点；原文不删
    importance   INTEGER DEFAULT 3,
    last_used_at INTEGER,
    use_count    INTEGER DEFAULT 0,
    pinned       INTEGER DEFAULT 0,
    suppressed   INTEGER DEFAULT 0
);
```

`messages` 表原样保留，作为原始记录。摘要压缩只新增 `memories`，不删原文。

## 四、权重

不用「分数」，用权重。

```
单条权重 = 关联度 × 时效 × 重要度
```

用乘法不用加法。加法的问题是：时间项一大，无关内容也能被推上来。乘法里任何一项接近 0，整体就接近 0，这才是直觉。

**关联度**（0–1，第一步实现）：标题、正文、关键词各自与当前问题的匹配度，取最高。

中文匹配用两个字一组（bigram），不用单字——「的、我、你」到处都是，单字会大量误命中。再去掉常用虚词。

**时效**（0–1）：

```
时效 = 0.5 ^ (距 last_used_at 的天数 ÷ 半衰期)
```

从「最后一次被用到」算，不从创建时间算。经常被重复提到的事会自己浮上来，不需要预设衰减曲线。半衰期是唯一要拍的参数，推荐 60 天，跑一阵再调。

**重要度**（0–1）：`importance / 5`。

写入时由模型打一个 1–5 分，**进库即固定，之后不重判**（避免同一个东西今天 4 星明天 2 星的系统抖动）。用户不认同可手动改。用户显式说「这个重要」，直接 `pinned = 1`，跳过打分。

## 五、排版

模型对上下文的注意力有位置效应：开头和结尾最容易被用上，中间容易被忽略。所以顺序固定为：

```
[人格层 persona.md]          ← 固定，最前
[事实：当前有效状态]          ← 最多 800 token
[情景：最近对话]              ← 最多 3000 token，从最新往回塞
[置顶记忆 + 主动联想的那一条]  ← 最后，紧贴当前问题
```

限的是 token 不是条数。同样 12 条，短的时候两千字，长的时候八千字，条数管不住长度。

## 六、摘要压缩

- 触发：情景层超预算，或隔天。
- 做法：把一段对话压成 3–5 句，写进 `memories`，`source_from` / `source_to` 指回原始消息。
- 原文不删。人记不住原话，但记得那天聊过什么；想翻回去的时候得翻得到。

## 七、冲突检测

写入 `facts` 时，按 `subject` 查已有条目。若内容矛盾：

1. 新条目照常写入；
2. 旧的 `superseded_by` 指向新的；
3. 旧条目仍可被检索到，但带「已过时」标注。

不删。删除会让「以前是怎样的」永久消失，而人恰恰靠这个理解变化。

## 八、创造层

地基是标准的检索架构。让它像人的，是下面这些，加在**检索层**而不是存储层。

1. **主动联想**：每轮在权重 top N 之外，另抽 1 条超过 14 天没被提起的旧记忆，作为「突然想起」。人就是这样想起不相干的事。
2. **复习回升**：权重公式里时效从 `last_used_at` 算，被用到就回升。这是记忆的强化，不是衰减的补偿。
3. **情绪加权**：写入时判这段对话的情绪强度，强度高的 `importance` 加 1。人记得最牢的多是情绪最强的时刻。
4. **压制**：`suppressed = 1` 的条目永不主动提起，但可被显式检索到。人也有刻意不提的事。

第 1 条有风险：可能提起不合时宜的事。所以配套「别再提这个」的开关，命中即置 `suppressed`。

|---|---|---|

| 事实层 token 预算 | 800 | |
| 情景层 token 预算 | 3000 | |
| 主动联想间隔 | 14 天 | |

## 十、实施顺序

**第一步**（不改框架，只改数据）

- 建 `facts`、`memories` 两张表；
- `persona.md` + 置顶记忆 + 当前状态 + 最近对话，按第五节排版拼上下文；
- 关联度只用 bigram 字面匹配；
- 不做向量、不做自动摘要、不做主动联想。

**第二步**（跑顺了再加）

- 摘要压缩；
- 冲突检测；
- 主动联想、情绪加权、压制。

## 十一、没解决的事

- 我没有跨对话记忆。这些都在文件里，每轮读到才「想起来」。方案不依赖模型内在状态，但也别指望它自己记着。
- 关联度用字面匹配，同义不同词会漏。这是第一步的已知缺陷，第二步再考虑向量。
- 权重公式的乘性结构没经过数据验证，是直觉推导。跑起来之后要用真实对话回头校准。

## 十二、落地记录

第一步和第二步一起做了，代码抽成了这个独立仓库：

| 文件 | 管什么 |
|---|---|
| `store.py` | `facts`、`memories` 两张表，以及存取、取代、封口 |
| `memory.py` | bigram 关联度、时效、权重、token 预算、拼上下文、`/想起` 的列表 |
| `extract.py` | 每轮抽状态与事件、情绪加权、摘要压缩 |
| `dream.py` | 每周离线核对，合并重复、按原文改错 |

网页版的命令和后台线程没有抽出来；`demo.py` 演示的是核心流程。

实现时定下的几件事：

- **排版落成三条消息**：第一条 `system` 放 persona + 时间 + 事实层；中间是情景层；再一条 `system` 放置顶、这次相关的、突然想起，紧贴用户这句话。不是在 persona 后面堆完所有记忆——那样最后一层就跑到中间去了。
- **token 是估的**：中文 1 字算 1 token，ASCII 4 字符算 1 token，宁多勿少。限的是 token，不是条数。
- **关联度阈值**：bigram 命中率低于 0.15 不进上下文。旧事实只在被问到时补进来，最多 2 条，标「已过时」。
- **主动联想**：从「超过 14 天没被提起」的条目里按重要度加权随机抽 1 条；抽中即算被用到，14 天内不会重复。不带编号发「/别再提」封最近抽中的那条。
- **摘要压缩**：情景层超过 3000 token，或跨天且积了 16 条以上，就在后台压最旧的 4–40 条，最近 10 条不动，一次最多压 40 条。`source_from` / `source_to` 指回原文，一条不删。
- **写入是后台线程**：主回复不等抽取；连着发几轮会排队，一次跑一个，不丢轮次。`.env` 里 `MEMORY_AUTO=0` 可关自动抽取，命令仍可用。
- **只记用户本人的状态**：抽取的事实带 `about` 字段，不是 `user` 的直接丢掉；朋友、家人、同事的事只进 `memories`（标题带上是谁），不占用户的状态槽。分不清是谁就不写 `facts`。
- **同名状态的判重**：同一个 `subject` 下，内容 bigram 的 Jaccard ≥ 0.75 视为同一条，只刷新使用时间；否则新增一行并把旧的 `superseded_by` 指过来。
- **命令**：`/想起` 看记忆，`/重要 编号` 置顶（F 开头是状态，M 或纯数字是记忆），`/别再提 编号` 封口，`/全忘 确定` 清空两层记忆（原文不删）。
- **参数可覆盖**：`MEMORY_HALF_LIFE`、`MEMORY_FACT_TOKENS`、`MEMORY_EPISODE_TOKENS`、`MEMORY_ASSOC_GAP`、`MEMORY_RECALL_TOKENS`，默认值就是第九节那张表。

已经验过的：临时库上跑通了事实取代、情绪加权、压制、情景预算、摘要覆盖点、命令全流程；`py_compile` 通过。**没验过**的是接真模型之后的抽取质量——抽得准不准、重要度给得合不合理，要跑一阵才知道。

没做：向量检索、跨用户、把重要度改低的入口、整理的回滚。多用户要等真有多用户再说。


## 十三、做梦与翻旧账

第十二节之后补的，补的是「纠错回路」，不加层。

- **`/翻 关键词`**：直接按字面搜 `messages` 原文，带编号、日期、是谁说的。旧账翻得到，核对才有依据。
- **做梦**：每周一次，或 `/做梦` 手动。自动触发要同时满足：距上次 ≥7 天、新增 ≥20 条消息、记忆 ≥5 条。失败了隔一小时再试，不每轮撞墙。
- **输入**：当前状态、记忆索引（不含置顶、封口、已合并的）、最近 80 条原文（压到 5000 字以内）。
- **只允许三种动作**，一次最多 8 条：合并重复、按原文改记忆、按原文改状态。合并只是把重复条目用 `merged_into` 挂到保留的那条下面，不删行。
- **状态修正照旧走版本化**：旧的标 `superseded_by`，新内容另起一行。`correct_memory` 是原地改笔记，因为记忆本来就是笔记，不是原文。
- **只认输入里出现过的编号**，越界的动作直接丢掉；整理记录写进 `dreams` 表，`/想起` 末尾会显示上次整理日期。
- **已知限制**：模型可能选错保留哪条，也可能把对的改错。没有回滚，只能靠 `/想起` 和 `/翻` 人工复核。这是把「显著性判断」交给模型的代价——Anthropic 那篇也是这么做的，区别是他们有更多评测兜底。
